1. Final design decision

The classic ESP32-WROOM-32 was rejected for this exact project because an 8-channel analog sensor consumes more ADC1 inputs than the classic ESP32 has while Wi-Fi is active. The new design uses ESP32-S3, whose ADC1 covers GPIO1–GPIO10. Eight of those channels are used for the QTR array, leaving plenty of normal GPIOs for the driver, servo, buzzer and I²C.

Why this is the correction: do not force a classic ESP32 to read eight analog QTR channels through ADC2 while Wi-Fi is running. The ESP32-S3 gives us eight clean ADC1 channels for the sensor and additional GPIOs for the rest of the robot.

5. Power system — the reliability fix

The old project shared the battery between the Arduino and motor system. The rebuild keeps one common ground, but gives the motors/servo and the ESP32 separate regulated rails.

Power tree

Mandatory reliability rules

  • Do not power the motors from an ESP32 pin.
  • Do not feed 7.4–8.4 V directly into a 6 V motor/servo rail.
  • Set each adjustable buck with a multimeter before connecting the electronics.
  • Use a 470–1000 µF electrolytic near the motor driver/servo rail.
  • Place a 100 nF ceramic capacitor across each brushed motor's terminals.
  • Keep motor wires short and physically separate from sensor signal wiring.
  • Use soldered/secure connectors in the final robot; avoid crocodile clips for power.
  • All modules share GND, but motor current should not return through the ESP32 wiring.
USB warning: Espressif specifies mutually exclusive power paths for the DevKit's external 5 V/3.3 V headers versus USB power. During standalone operation, power from the 5 V buck; during USB programming/debug, disconnect the battery-powered 5 V rail unless your exact board/setup provides appropriate power isolation.
Software rule: Wi-Fi connection must never block startup. The robot boots hardware first, creates its local access point/web server, and continues operating even if the phone is not connected.

6. Sensor calibration + PID

Calibration sequence

1
Start CALIBRATION.
Keep the motors stopped.
2
Sweep the sensor across white and black.
Move left ↔ right for several seconds so every sensor sees both surfaces.
3
Store per-channel minimum/maximum.
Use calibrated readings rather than fixed raw thresholds.
4
Save to flash.
Next startup keeps the calibration until recalibrated.

PID tuning order

A
Ki = 0
Start with proportional + derivative control.
B
Raise Kp gradually.
Stop increasing when oscillation around the line becomes obvious.
C
Raise Kd.
Use it to damp the oscillation and improve corner recovery.
D
Adjust base speed last.
Sharp error → lower speed automatically.

7. Line-loss recovery

TRACK
normal PID
SEARCH
last known direction
STOP
timeout safety state

When all sensors lose the line, do not simply keep driving forward. Remember the last error direction, slow down, search toward that side, and stop with an alert if the line is not recovered within a short timeout.

8. Car body + medicine box

The base chassis is the inexpensive 2WD acrylic smart-car body. Add a lightweight upper deck for electronics and a small medicine compartment above the rear/center.

Mechanical priorities

  • Sensor board must be rigid and parallel to the floor.
  • Keep the sensor centered on the robot's longitudinal centerline.
  • Keep the battery low to reduce tipping and wheel lift.
  • Keep the medicine box lightweight.
  • Protect the QTR board with a small dark hood/skirt from stray light.

Suggested track

  • Matte white background.
  • Matte black tape line, consistent width.
  • No shiny floor for the first tuning sessions.
  • Start with wide curves before sharp corners.

9. Assembly order

1
Build the 2WD body.
Install motors, wheels and caster. Mount the QTR board at the front.
2
Build the power section separately.
Battery → fuse → switch → both buck converters. Set 6.0 V and 5.0 V with a multimeter before connecting loads.
3
Connect TB6612 + motors.
Power the driver logic from 3.3 V and the motor rail from 6.0 V.
4
Connect the QTR array.
All eight outputs go to the S3 ADC1 pins listed above.
5
Connect the servo and optional sensors.
Servo gets 6 V; I²C sensors stay on the 3.3 V logic side.
6
Upload firmware with USB power only.
Do the first firmware test with motors disconnected.
7
Test each subsystem independently.
Sensor → motor driver → servo → web UI → full robot.

10. Pre-power + test checklist

Before connecting the battery

  • ☐ Battery is a 2S LiPo and not damaged/swollen.
  • ☐ Fuse is installed.
  • ☐ Main switch is OFF.
  • ☐ XL4015 output measured at 6.0 V.
  • ☐ LM2596 output measured at 5.0 V.
  • ☐ QTR VCC is 3.3 V.
  • ☐ No accidental short between 5 V, 6 V and 3.3 V rails.
  • ☐ Common GND is connected.

Test order

  • ☐ ESP32 boots with motors disconnected.
  • ☐ Serial reports the reset reason.
  • ☐ Phone can connect to the robot's Wi-Fi AP.
  • ☐ Live sensor bars respond to black/white.
  • ☐ Motor 1 direction verified.
  • ☐ Motor 2 direction verified.
  • ☐ Servo opens/closes the hatch.
  • ☐ Calibration completes.
  • ☐ Low-speed straight line test.
  • ☐ Curve test → sharp corner test → full route.
What a reset means: if the ESP32 restarts when motors/servo start, inspect the power system first. A voltage dip/brownout or noisy return path is more likely than a mysterious PID problem.
